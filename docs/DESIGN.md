## 1. 구성

관제 코어는 두 실행 형태에서 같은 코드로 돕니다. 시뮬레이션 관제탑(`fleet.server`)은 현장을 프로세스 안에서 모의하고, 실운영 관제 서비스(`fleet.fms`)는 MQTT 브로커 건너편의 차량을 상대합니다.

```
┌──────────────────────── 현장 ─────────────────────────────────────────────────────┐
│ 시뮬레이션: 차량(VDA 5050 클라이언트) · 사람 · 수동 지게차 · 타사 로봇 · 고속문 · 카메라 │
│ 실운영: 실차 / 벤더 시뮬레이터 / fleet.agvsim(차량 + 고속문 제어기 모의)             │
└───────┬──────────────────────────────────────────────┬────────────────────────────┘
        │ uagv/v2/{제조사}/{차량}/order|instantActions|   │ facility/v1/door/{id}/request|state
        │ state|visualization|connection|factsheet      │ facility/v1/fire/state, 카메라 감지
┌───────▼────────────── 메시지 버스 ─────────────────────────────────────────────────┐

│ 실운영: MQTT 3.1.1(fleet/mqtt.py) + 공식 JSON 스키마 수신 검사(fleet/schema.py)     │
└───────┬───────────────────────────────────────────────────────────────────────────┘
┌───────▼──────────── 관제 코어 FleetManager (fleet/control.py) ────────────────┐

┌───────▼─────── 작업 배정 Dispatcher ───┐ ┌─▼──── 운영 Operations ───────────────────┐
│ 현장 공정(DcProcess, TransportProcess) │ │ 명령 · 확인 절차 · 감사 로그 · 읽기 전용 ·   │
│ 비용 기반 배정 · 충전·주차 · 예외 처리  │ │ 교대 인계 · WMS 주문 접수(멱등)             │
│ WMS 이벤트 outbox                      │ └─▲───────────────────────────────────────┘
└────────────────────────────────────────┘   │ HTTP · SSE (fleet/server.py) + 계정·권한(fleet/auth.py)
                                   ┌─────────┴───────── 관제 화면(web/) ───────────┐
```

- 관제 코어는 버스로 들어온 메시지로만 현장을 압니다. 시뮬레이션의 실제 위치는 평가기(접촉·근접사고 판정)와 지도의 "실제 위치(평가)" 레이어에만 쓰입니다. 운영 화면의 수치는 관제가 아는 값이고, 평가기 값은 평가 레이어를 켰을 때만 "평가:"를 붙여 보입니다.
- 관제 시계는 주입합니다(`fleet/clock.py`). 시뮬레이션은 시뮬레이션 시계, 실운영은 실시간 시계를 씁니다.
- 가상 운영자(`fleet/autoop.py`)는 사람 운영자와 같은 명령·SOP·감사 경로를 씁니다. 벤치마크와 무인 시연에서 켜며, MTTA(확인까지 시간)를 기록합니다.

## 2. 충돌 관리 3계층

상용 FMS 문서(MiR Fleet, OTTO)는 충돌 관리를 세 계층으로 나눕니다(R2 B-2). 이 시스템도 같은 구분을 따르고, 각 계층이 못 막는 사고를 다음 계층이 받습니다. 사람 보호의 책임은 ③ 차량 탑재 안전 기능에 있고, ①·②는 위험 노출을 줄이는 운영 계층입니다([SAFETY.md](SAFETY.md) 1·2절).

| 계층 | 구현 | 막는 것 | 못 막는 것 |
|---|---|---|---|
| ① 계획 단계: 자원 예약 | 노드 배타 잠금, 무방향 차선 잠금, 앞 3노드 선행 예약. 교차로·문턱은 통과까지 한 번에 예약(최대 4노드, 끝이 문턱 정차 금지 노드면 8노드까지). 제자리 회전 시 회전 원 안의 노드 추가 예약 | 로봇끼리의 정면·교차 충돌, 교차로 안 정차, 회전 중 스침 | 예약에 들어오지 않는 유닛(사람·수동 지게차), 통신 지연 중 실제 위치 |
| ② 실행 단계: 관측 기반 감시 | 사람·지게차 추적을 예측 원판(사람 2 s, 지게차 4 s)으로 바꿔 해당 노드·차선 예약 차단. 주행 중 지게차 앞 교차로의 선회 영역 선점. 타사 로봇은 공개 일정(ETA)으로 예약. 점유-예약 대조가 예약 밖 점유를 1.5 s 넘게 보면 해당 차량 일시정지 | 사람·지게차 앞으로 새로 진입하는 것, 예약 규칙 위반 | 사각지대(카메라 범위 밖)의 사람, 갑자기 뛰어드는 사람, 규칙을 어기는 운전자 |
| ③ 차량 자체 안전 | 속도 비례 보호·경고 필드, 좁은 필드 세트(0.3 m/s 이하), 360° 근접 필드, 회전 원 필드, 범퍼, 안전 고장 원격 리셋 거부 | 관제가 모르는 장애물, 관제 오류 | 필드 밖(높이·평면 밖) 장애물. 이 한계는 OTTO 매뉴얼이 명시(R2 B-2) |

결과 지표는 평가기가 실제 위치와 차체 모양(직사각형·원)으로 셉니다. 접촉은 정지 중 접촉까지 모두 세고, 근접사고는 달리는 차량 앞, 차체가 쓸고 지나갈 폭 안, 정지 엔벨로프(반응 0.2 s + 제동 거리 + 0.05 m) 안에 사람이 들어온 경우입니다. 속도를 판정 임계 아래로 낮추는 것만으로는 0이 되지 않도록 정한 정의입니다. 지표 전체 정의는 [SAFETY.md](SAFETY.md) 5절에 있습니다.

## 3. 교통 제어

### 3.1 왜 예약 방식인가

MAPF 계열(CBS, PIBT 등)은 한 번에 최적 경로를 풀지만, 실행 오차·통신 지연·명령할 수 없는 유닛이 있으면 계획이 곧 무효가 됩니다(R1 §2.2, §2.6). 상용 FMS도 자원·구역 예약과 교착 감지를 쓴다고 문서화합니다(R2 B-2의 MiR). 이 시스템은 다음 구조를 택했습니다.

- 경로는 시간 기반 A*로 구합니다(간선 길이 ÷ 제한 속도). 가중치에 회전 비용, 다른 차량이 점유한 노드, 최근 대기 누적(반감기 180 s)을 넣습니다.
- 실행은 VDA 5050의 base/horizon으로 조금씩 풀어 줍니다. 예약에 성공한 구간만 base로 보내고, 그 뒤는 horizon으로 보여만 줍니다.
- 교착은 사후에 탐지해 해소합니다.

### 3.2 교착 탐지·해소

| 단계 | 방법 |
|---|---|
| 탐지 | 대기 관계(로봇 → 막고 있는 로봇) 그래프에서 순환을 찾고 2초간 유지되면 확정. 예약 대기와 주행 경로의 보호정지를 함께 봄. 필드 원인이 보고되면 해당 로봇을 쓰고 사람·지게차·외부 로봇 원인은 로봇 간 순환에서 제외. 원인이 없는 표준 state는 바로 앞 4 m 안 로봇의 위치로 추정. 충전·작업 동작·유휴 상태는 보호정지 대기 간선을 만들지 않음. 한 로봇이 상대가 선회에 필요한 노드를 쥔 채 그 상대 때문에 보호정지한 순환도 잡힘 |
| 1차 해소 | 순환 중 새 주문을 받을 수 있는 로봇이 상대가 쥔 노드를 피해 재계획. 이미 해제된 경로를 마친 노드에서만 바꾸며, 구간 중간·충전·작업 동작 중인 로봇은 제외 |
| 2차 해소 | 재계획이 없으면 빈 노드나 주차 스텁으로 비켜섬(evasion). 통과만 할 노드와 들어갈 수 없는 노드를 구분 |
| 알람 | 30초 안에 풀리지 않으면 DEADLOCK_UNRESOLVED(2순위)와 SOP |

비교 기준선으로 전략 세 가지를 둡니다: `none`(관제 없음, 차량 안전 필드만), `locks`(예약만), `locks+resolve`(예약 + 교착 해소). 결과는 [BENCHMARK.md](BENCHMARK.md)에 있습니다.

### 3.3 속도 규칙

| 규칙 | 값 | 근거 |
|---|---|---|
| 교차로 | 반경 1.5 m 안 1.39 m/s(5 km/h), 들어가기 전 미리 감속 | KOSHA·UKMHA 보행 혼재·교차로 5 km/h(R3 §0.2) |
| 사각 교차로 | 1.0 m/s. 들어오는 두 차선의 3 m 뒤 점끼리 랙·벽에 가리면 사각 | AGF 정지 거리가 1 m 안에 들도록 정한 추론값([SITE.md](SITE.md) 2절) |
| 협업 피킹 | 사람이 추적되는 피킹 통로만 0.3 m/s(통로 단위). 동 전체 제한(`zone`)과 차량 필드만(`vehicle`)을 벤치마크로 비교 | ISO 3691-4 여유 공간 축소 조건(2차) |
| 표준 폴백 | 차량이 `x_fleetSpeedLimit`을 지원하지 않으면 구역 제한을 order 간선의 `maxSpeed`에 넣음 | VDA 5050 2.0 |

처음 설계는 이웃이 3개 이상인 모든 노드에 0.6 m/s를 걸었고, 피킹 동에 사람이 한 명만 있어도 동 전체를 0.3 m/s로 묶었습니다. 현업 기준과 대조해 위 값으로 바꿨고, 바꾼 효과는 BENCHMARK.md의 생산성 비교에 있습니다.

### 3.4 레이아웃 규칙

교통 제어 성능은 알고리즘만큼 레이아웃에 달려 있습니다. R1 §2.5의 일방통행 권고를 따르되, 개발 중 실제로 교착을 만든 지점을 규칙으로 바꿨습니다.

- 1차선 양방향 구간은 정면 교착을 만듭니다. 주통로는 2차선, 통로·척추는 일방통행으로 둡니다. 양방향 격자(`grid-deadlock`)는 비교 기준선으로만 남겼습니다.
- 교차로 사이에 설 곳이 없으면 교차로 안에서 기다리게 됩니다. 4 m 이상 구간마다 대기 노드를 둡니다.
- 회전 지점은 주차면·문에서 떨어뜨립니다. 2.7 m 지게차의 회전 원(반경 약 3 m 예약)이나 보호 필드가 주차 차량에 걸리면 물리적 교착이 되는데, 이는 예약 순환에 나타나지 않습니다.
- 한 문이 막히면 갈 수 없는 구역이 없게 합니다. 동측 복귀로(AGF 남행)를 둬서 남·북 고속문 어느 쪽이 고장 나도 출고 스테이징에 갑니다.

## 4. VDA 5050 매핑

기반은 2.0.0입니다(order, instantActions, state, visualization, connection, factsheet). 표준에 없는 기능은 `x_` 접두사 확장으로 두고 차량 factsheet의 `protocolFeatures.agvActions`에 선언합니다. 관제는 factsheet를 보고 차종(agvClass)과 지원 액션을 판단하며, 확장을 지원하지 않는 차량에는 표준만 써서 같은 결과를 냅니다(표준 폴백).

| 항목 | 표준 여부 | 쓰임 |
|---|---|---|
| order base/horizon, released 규칙, 짝수·홀수 sequenceId | 2.0 | 예약된 구간만 released |
| orderUpdate 이어 붙이기 | 2.0 | base 끝에서만 이어 붙이고, 새 orderId는 base를 끝낸 뒤에만 보냄. 거절되면 재동기화 |
| order·action id | 2.0 | 관제 실행 ID를 접두사로 붙여 재기동 뒤에도 겹치지 않음 |
| nodePosition theta, allowedDeviationXY | 2.0 | 스테이션 진입 방향(-π–π), 삼륜 AGF의 정차 자세 |
| startPause, stopPause, cancelOrder, initPosition, factsheetRequest, stateRequest | 2.0 | 일시정지·일괄 정지 폴백·취소·위치 재지정 |
| pick, drop(`lhd` FORKS, `side`, `stationName`, 높이), startCharging, stopCharging | 2.0 | 팔레트 픽·드롭(소요 시간은 차량이 정함), 충전 |
| `safetyState.fieldViolation` | 2.0 | 보호정지 판정의 1차 근거 |
| `x_toteInduct`, `x_pickItems`, `x_toteDrop` | 확장 | 협업 피킹. `x_pickItems`는 피커가 옆에 와야 끝남 |
| `x_fleetSpeedLimit` | 확장 | 구역 감속(3.0의 zone 개념, R1 §1.2.5). 미지원 차량은 간선 `maxSpeed` |
| `x_remoteStop`, `x_resetFault`, `x_fieldServiceDone`, `x_setOperatingMode`, `x_teleop` | 확장 | 일괄 정지(미지원 시 `startPause`), 비안전 고장 원격 리셋, 현장 조치 완료, 수동 인계, 원격 조종 |
| state `x_safetyField`, `x_detections` | 확장 | 필드 원인 표시, 차량 센서의 사람·지게차 감지 |
| batteryState.reach, factsheet protocolLimits(timing, maxStringLens, maxArrayLens) | 2.0 | 주행 가능 거리, 기대 수신 주기(통신 감도 계산), 메시지 길이 한계 |

메시지는 공식 2.0.0 JSON 스키마로 검사합니다. 실운영 서비스는 받은 메시지를 모두 검사해 위반을 버리고 세며, 관제와 차량 모델이 보내는 메시지는 시험으로 스키마 통과를 고정했습니다. 선택 필드(`velocity`, `agvPosition` 등)가 없어도 관제 주기는 멈추지 않습니다. 자세한 내용은 [INTEGRATION.md](INTEGRATION.md) 4절에 있습니다.

## 5. 통제 불가 유닛

| 유닛 | 관제가 아는 것 | 처리 |
|---|---|---|
| 사람 | 천장 카메라(지연·오차·미검출·오분류·오검출 모델, 범위는 `none`·`partial`·`full`)와 차량 센서의 점 감지 | 알파-베타 추적, 2회 관측으로 확정, 클래스 다수결, 겹친 트랙 병합, 3 s 미관측 시 소멸. 예측 원판으로 예약 차단. 협업 구역(피킹·패킹)에서는 사람이 자기가 선 정차점(0.5 m 안)만 막고, 옆을 지나는 일은 통로 감속과 차량 좁은 필드에 맡김. 인프라 피드가 3 s 끊기면 사람 구역 전체 감속과 알람 |

ANT locator 사례(R2 B-2) |
| 타사 로봇 | 위치·일정(ETA)을 어댑터로 받음(명령 불가) | 일정에 있는 노드·차선을 그 유닛 이름으로 예약해 우리 로봇이 피함. Open-RMF read-only 함대와 같은 개념(R1 §1.1.4) |

피킹 동에는 작업 방출 상한(CONWIP)을 둡니다. 동시에 진행하는 토트 작업을 피킹 통로당 3건(5개 통로면 15건, `pick_aisle_capacity`)까지만 배정하고, 나머지 토트 AMR은 주차면에서 기다립니다. 처리할 수 있는 것보다 많은 로봇을 내보내면 토트 척추와 주통로에 대기열이 생기고, 그 꼬리가 지게차 동선을 막아 현장 전체가 멈췄기 때문입니다(BENCHMARK.md 결함 표). 같은 이유로 차량 대수는 대기 자리(주차·충전, 토트 AMR은 패킹 스테이션 포함)를 넘지 않게 정하며, 넘으면 시뮬레이션이 경고합니다.

사람과 지게차 모델에는 규칙 위반이 들어 있습니다. 사람은 이동의 2 %를 차량을 신경 쓰지 않고 걷고, 지게차는 막혔을 때 먼저 최대 4.5 m(무전 요청 뒤 6 m) 후진해 양보하되 후진할 수 없으면 30 s 뒤 10 %가 그대로 회전합니다. 관제와 차량이 이런 상황을 받아 내는지가 안전 지표에 드러납니다.

## 6. 설비 연동: 고속문과 화재 경보

R2 C-1 #7은 "모의 엘리베이터·자동문·충전기와 실패 주입"을 필수 항목으로 꼽고, 공개 문서에 실패 처리 절차가 없다고 적었습니다. 그래서 절차는 이 프로젝트에서 설계했고, 메시지는 Open-RMF의 DoorRequest/DoorState 형식을 따랐습니다(R1 §1.1.6).

| 단계 | 동작 |
|---|---|
| 요청 | 경로상 15 m 안에 문이 있거나 문을 기다리는 차량이 있으면 1초 주기로 열림 요청(`facility/v1/door/{id}/request`). 문 차선을 이미 예약한 차량이 있으면 문이 사용 중지·고장 판정이어도 요청을 유지해, 그 차량 앞에서 문이 닫히지 않게 함 |
| 예약 | 문이 OPEN을 보고하는 동안만 문턱 차선을 예약할 수 있음. 문턱 1.9 m 안 노드는 정차 금지 |
| 닫힘 | 마지막 요청 5 s 뒤 닫힘. 문턱 0.9 m 안에 물체가 있으면 닫지 않음(문 자체 센서) |
| 고장 판정 | 요청 후 10 s 미개방(무신호 걸림), 제어기 3 s 무응답(기동 후 한 번도 보고가 없으면 "제어기 미연결"), 고장 신호. 원인별로 판정 |
| 대응 | FACILITY_FAULT(2순위) 알람, 해당 문을 경로에서 제외, 문 앞 대기 차량은 즉시 우회. 우회 경로는 쓸 수 없는 모든 문을 피할 때만 채택하고, 없으면 그 문 앞에서 기다림(두 문 사이 왕복 방지). 문 앞 대기의 장시간 정지 알람은 그 문의 FACILITY_FAULT가 활성일 때만 억제하고, 운영자가 사용 중지한 정상 문 앞 대기는 알람과 재시도 안내를 띄움 |
| 복구 | 무응답·고장 신호는 문이 정상 보고하면 자동 해제. 무신호 걸림은 문이 OPEN을 보고하거나 운영자가 현장 조치 뒤 재시도할 때만 해제(자동 해제하면 다시 걸린 문으로 차량을 보냄) |
| 화재 경보 | 화재 수신기(`facility/v1/fire/state`)가 경보를 내면 문은 문턱이 비는 대로 닫히고 열림 요청을 거부함. 관제는 FIRE 모드로 신규 해제·배정을 멈추고, 차량은 이미 받은 구간 끝에서 정지(구간 끝은 문턱·교차로가 아님). 경보가 풀리면 전체 일시정지로 두고 운영자가 현장 확인 뒤 재개 |

닫힌 문의 커튼은 물리 장애물이기도 합니다. 관제가 실수로 문을 예약해도 차량 보호 필드가 멈춥니다(③ 계층). 실제 현장에서는 방화 셔터를 화재 수신기에 배선으로 연동하고, 관제 반응은 그 보조입니다.

## 7. 통신 두절

- 3 s 동안 state·visualization이 없으면 CONNECTIONBROKEN으로 보고 통신 지연 알림을 띄웁니다. 예약은 유지해 다른 차량이 그 자리로 들어가지 않게 합니다. Wi-Fi 로밍 같은 짧은 끊김은 운영자 조치가 필요 없으므로 알림으로 둡니다.
- 30 s 넘게 이어지면 통신 두절 알람(3순위)이 되고, 적재 전 작업은 다른 차량에 재할당합니다.
- 차량은 이미 받은 base 끝까지만 가고 멈춥니다. MiR은 5분 뒤 예약 없이 진행을 허용하지만(R2 B-1), 이 시스템은 사람이 있는 현장이라 허용하지 않습니다.
- 재연결되면 state의 orderId·orderUpdateId로 재동기화하고, 받지 못한 order는 2.5 s 주기로 재전송합니다.
- 통신 감도는 factsheet의 기대 주기 대비 최근 5 s 수신율과 지연 중앙값으로 표시합니다. 표시 항목(식별·위치·속력·배터리·통신 감도·원격 정지)은 국내 실외이동로봇 운행안전인증 고시의 관제장치 요건(R2 §0)을 참고해 골랐습니다. 이 고시는 실외 로봇 대상이라 실내 물류센터에 법적으로 적용되지 않으며, 화면 구성의 점검표로만 썼습니다.

## 8. 알람

ISA-18.2 / IEC 62682의 용어와 수명주기를 따릅니다(R1 §4.1).

- 상태: 미확인(UNACK), 확인(ACKED), 정상 복귀·미확인(RTN_UNACK), 보류(SHELVED)가 있습니다.
- 우선순위는 "운영자가 늦게 대응하면 생기는 결과"로 정했습니다(합리화). 차량이 스스로 안전하게 멈춰 있고 늦어도 처리량만 잃는 상황은 3순위입니다.
  - 1 긴급(즉시): 사람 접촉, 충돌, 화재 경보, 관제 내부 오류
  - 2 높음(5분 안): 점유-예약 불일치, 교착 해소 실패, 인프라 감지 두절, 설비 이상, 알람 홍수
  - 3 보통(30분 안): 로봇 고장, 위치 상실, 통신 두절(30 s), 대치(보호정지 60 s), 배터리 위험, 장시간 정지(120 s, 사람·지게차 대기 300 s), 작업 지연
  - 4 알림(사후 검토, 확인 불필요, 알람률에서 제외): 운영자 자신이 건 일괄 정지, 근접사고, 통신 지연(3 s), 혼잡, 봉쇄 구역 대기, 충전기 부족
- 모든 알람 유형에 자동 조치, 운영자 절차, 바로 실행할 명령 버튼이 붙어 있습니다(`fleet/alarms.py`).
- 채터링이 잦은 유형(대치, 장시간 정지, 혼잡, 작업 지연, 봉쇄 구역 대기, 충전기 부족)은 조건이 30 s 이어서 사라져야 해제합니다(해제 지연). 혼잡은 데드밴드(35 % 이상이 60 s 지속되면 발생, 25 % 미만에서 해제)를 씁니다.
- 파생 알람은 억제합니다. 대기 사슬의 뿌리만 장시간 정지를 올리고, 고장·두절·원격 조종 차량 뒤의 대기와 고장 알람이 활성인 문 앞의 대기는 그 원인 알람이 대표합니다. 원인 알람이 없는데 억제만 남는 경우(사용 중지된 문)는 만들지 않습니다.
- 1순위는 보류할 수 없고, 보류에는 사유와 만료가 있습니다. 10분에 10건을 넘으면 알람 홍수 알람을 올립니다. 알람 수는 우선순위별·유형별로 따로 셉니다.

## 9. 운영 명령과 안전 규칙

- 계정은 viewer·operator·supervisor 세 역할이고, 훈련 주입·시뮬레이션 제어는 supervisor만 합니다. 감사 로그에는 인증된 계정 이름이 남고, SQLite에 HMAC 체인으로 저장해 변조를 검사할 수 있습니다([INTEGRATION.md](INTEGRATION.md) 7절).
- 여러 로봇에 걸리는 명령(일괄 정지·전체 정지·구역 봉쇄·대피·원격 조종 인계)은 확인 플래그 없이는 거부합니다.
- "일괄 정지(비안전)"는 무선 소프트웨어 정지입니다. 해제하면 전체 일시정지(HOLD)로 두고, 재개는 따로 해야 합니다. 비상정지 해제 뒤 임의로 움직이지 않게 하는 관행(R2 B-1)을 따른 것이며, 차량·현장의 비상정지 장치를 대신하지 않습니다.
- 안전 관련 고장(센서 이상, 범퍼)은 원격으로 리셋할 수 없습니다. 차량은 `x_resetFault`와 무선 `x_fieldServiceDone`을 모두 거부하고 관제도 원격 리셋 명령을 거부합니다. 현장 인원이 차량에서 리셋해야 풀리며(시뮬레이션은 이 현장 리셋을 모의), "현장 조치 완료" 등록은 기록으로 남습니다.
- 원격 조종은 0.6 s 데드맨이고, 조종 중에는 시뮬레이션을 1배속 이하로 묶습니다. 화면에 차량 주변 로컬 뷰를 보여 줍니다.
- WMS 주문은 `order_id`를 멱등 키로 받습니다. 같은 내용이면 기존 작업을 돌려주고(200), 내용이 다르면 거부합니다(409).

| 결정적 시뮬레이션(시드) | 같은 시드면 같은 결과. 벤치 결과를 명령줄로 추적 | 시간 압축된 배터리 등 모델 단순화 |
| 관제 주기 단일 스레드 | 네트워크 스레드는 큐에 넣기만 하므로 관제 상태에 잠금이 필요 없음 | 주기 하나가 늦으면 전체가 늦음 |
| 가상 운영자 | 긴 벤치가 사람 조치가 필요한 알람에서 멈추지 않음. MTTA·MTTR 측정 | 응답 지연은 분포 가정 |
