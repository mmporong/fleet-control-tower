# 관제 운영 절차(Runbook)

관제원이 이 시스템으로 한 교대를 운영할 때 따르는 절차입니다. 상황별 대처는 상용 FMS 문서(MiR Fleet, OTTO)의 방식과 ISA-18.2 알람 수명주기를 따릅니다([research/02_jobs_and_incident_response.md](research/02_jobs_and_incident_response.md)(R2) B-1·B-2·B-3, [research/01_standards_traffic_safety_ops.md](research/01_standards_traffic_safety_ops.md) §4.1). 관제원 → 현장 → 개발로 이어지는 역할 분담만 채용 공고에 나타난 조직 구성(R2 A)을 참고했습니다. 모든 알람의 자동 조치·절차·명령 버튼은 `fleet/alarms.py`에 정의되어 있고, 화면 알람 대기열에서 알람을 펼치면 같은 내용이 체크리스트로 보입니다.

안전 원칙은 [SAFETY.md](SAFETY.md)를 따릅니다. 관제의 "일괄 정지"는 무선 소프트웨어 정지이며 비상정지가 아닙니다. 센서 이상·범퍼 같은 안전 관련 고장은 원격으로 리셋할 수 없고, 현장 인원이 차량에서 확인한 뒤 "현장 조치 완료"로 풉니다.

## 1. 교대 흐름

| 시점 | 할 일 | 화면 |
|---|---|---|
| 교대 시작 | 로그인(개인 계정). 이전 교대의 인수인계 메모와 현재 상황 요약 확인 | 이벤트·감사 탭 → "현재 상황 요약 받기" |
| 시작 점검 | 운영 모드(정상·일시정지·일괄 정지·화재·재동기화), 통신 두절·고장·원격 조종·일시정지 차량, 봉쇄 구역, 고속문 상태, 인프라 감지 연결 확인 | 상단 리본, 차량 목록(예외 우선 정렬), 구역 제어 탭 |
| 근무 중 | 알람 대기열을 우선순위 순서로 처리, 조치는 SOP 버튼으로 실행(감사 로그에 계정 이름으로 남음) | 알람 대기열, 지도 |
| 사고 발생 | 사고 기록(전 30초·후 10초)을 재생해 경위 확인, 보고서 작성 | 사고 기록·재생 탭 |
| 교대 종료 | 조치 중인 사항·주의 구역·다음 교대 요청을 메모로 남김. 시스템이 알람·고장·봉쇄·교착·지표를 자동 요약해 같이 저장. 로그아웃 | 이벤트·감사 탭 → "인수인계 기록" |

## 2. 알람 처리 원칙

우선순위는 "운영자가 늦게 대응하면 생기는 결과"로 정했습니다. 차량이 스스로 안전하게 멈춰 있고 대응이 늦어도 처리량만 잃는 상황은 3순위, 운영자의 확인이 필요 없는 상황은 4순위 알림으로 내렸습니다(ISA-18.2 합리화).

| 우선순위 | 응답 | 알람 | 보류 |
|---|---|---|---|
| 1 긴급 | 즉시 | 사람 접촉, 충돌(범퍼), 화재 경보, 관제 내부 오류 | 불가 |
| 2 높음 | 5분 안 | 점유-예약 불일치, 교착 자동 해소 실패(30초), 인프라 감지 두절, 설비(고속문) 이상, 알람 홍수 | 사유와 만료(10·30·60분)를 적어 보류 가능 |
| 3 보통 | 30분 안 | 로봇 고장, 위치 추정 실패, 통신 두절(30초 이상), 대치(보호정지 60초), 배터리 위험, 장시간 정지(120초, 사람·수동 지게차 대기는 300초), 작업 지연 | 〃 |
| 4 알림 | 사후 검토 | 관제 일괄 정지 중(운영자 자신이 건 것), 근접사고, 통신 지연(3초), 혼잡, 봉쇄 구역 대기, 충전기 부족 | 확인 불필요, 알람률에서 제외 |

- 확인(ACK)은 "봤고 책임진다"는 뜻입니다. 조치 완료가 아닙니다. 조건이 사라져도 확인하지 않은 알람은 "정상 복귀·미확인"으로 남습니다.
- 알람 홍수(10분에 10건 초과)가 뜨면 1순위부터 처리하고, 같은 원인의 알람은 묶어 판단합니다. 원인 구역을 일시정지해 신규 알람을 줄입니다.
- 파생 알람은 시스템이 억제합니다. 고장·두절·원격 조종 차량이나 고장 난 문 뒤에서 기다리는 차량은 따로 알람을 올리지 않으므로, 원인 알람을 먼저 처리합니다.
- 짧은 통신 끊김(Wi-Fi 로밍 등)은 알림입니다. 차량은 받은 구간 끝에서 스스로 멈추고 예약은 유지되므로, 30초 넘게 이어질 때만 알람으로 올라갑니다.

## 3. 상황별 대응

R2 B-1의 표 형식(감지 → 1차 자동 → 관제원 → 현장 → 재개 조건 → 기록)입니다.

| 상황 | 감지 | 1차 자동 대응 | 관제원 조치 | 현장 조치 | 재개 조건 | 기록 |
|---|---|---|---|---|---|---|
| 보호정지(사람·물체) | 차량 state `safetyState.fieldViolation` | 차량이 즉시 정지 | 원인 유닛 확인. 60초 넘게 이어지면 STANDOFF 알람: 지게차면 무전으로 양보 요청, 사람이면 현장 안내, 공간이 있으면 원격 조종으로 후진 | 물체 제거 | 필드가 2초 비면 자동 재개 | 보호정지 횟수·위치(혼잡 레이어), 60초 초과 시 알람 이력 |
| 사람 접촉 | 범퍼 + 접촉 판정 | 해당 차량 범퍼 정지, 반경 6 m 차량 일시정지 | 부상 확인 최우선, 구역 봉쇄, 차량 수동 모드로 격리 | 부상 대응, 현장 통제, 차량에서 범퍼 리셋 | 안전 담당 확인 → 현장 조치 완료 → 주변 재개 | 사고 기록 자동 저장, 사고 보고서 |
| 로봇끼리 충돌 | 범퍼 | 관련 차량 정지(안전 관련 고장: 원격 리셋 불가) | 사고 재생으로 진입 순서·예약 확인 | 손상 확인, 차량에서 리셋 | 현장 조치 완료 등록 | 사고 보고서, 예약 불일치가 원인이면 구간 봉쇄 |
| 관제 일괄 정지(비안전) | 운영자 명령(사유 필수) | 전체에 `startPause`(지원 차량은 `x_remoteStop`) | 사유 기록, 현장 안전 확인. 사람이 위험하면 현장 비상정지 버튼이 우선 | — | 해제하면 전체 일시정지로 전환. 재개는 따로, 구역별 순차 | 감사 로그(누가 걸고 누가 풀었는지) |
| 로봇 고장 | state errors FATAL | 차량 자체 정지, 예약 유지(다른 차량 진입 방지), 신규 배정 중단 | 비안전 고장(구동부 등)만 원격 리셋 1회. 실패하거나 안전 관련 고장이면 작업 재할당·현장 요청 | 점검·수리, 적재물 회수, 차량에서 리셋 | 현장 조치 완료 등록 → 자동 모드·위치 확인 | 고장 유형·위치, MTTR |
| 위치 상실 | state positionInitialized = false | 정지, 주문 거부 | 마지막 노드와 대조해 위치 재지정(노드 1 m 안이어야 성공). 실패하면 막힌 작업 재할당 | 원격 조종으로 가까운 노드 0.6 m 안까지 옮기거나, 현장 인원이 옮기고 재위치 추정 후 현장 조치 완료 | 위치 확인 후 자동 전환 | 발생 위치(간선 한가운데 상실은 교차로를 오래 막음) |
| 통신 두절 | 3초 무수신은 알림, 30초 무수신은 알람 | 예약 유지. 차량은 받은 구간 끝에서 자체 정지. 30초에 적재 전 작업 재할당 | AP·전원 확인 요청, 적재 중이면 현장 회수 판단 | AP·전원 점검 | 재연결 후 주문 ID·위치 재동기화(자동) | 두절 구간·시간, 통신 감도 추이 |
| 인프라 감지 두절 | 카메라 피드 3초 무수신 | 사람 작업·보행·피킹 구역 전체 사람 감속 | 사각지대 구역 봉쇄 판단 | 카메라·서버 점검 | 추적 수가 평소 수준으로 복귀 | 두절 시간 |
| 고속문 이상 | 요청 후 10초 미개방, 3초 무응답(한 번도 보고 없으면 "제어기 미연결"), 고장 신호 | 문을 경로에서 제외, 문 앞 대기 차량 즉시 우회(다른 쓸 수 있는 문이 있을 때만), 이미 문 차선을 예약한 차량은 통과시킴 | 영향 차량 확인, 우회 경로가 없는 작업은 재배정 검토. 수리 동안 "사용 중지"(고장 신호가 먼저 풀려도 사용 중지는 남으므로 수리 뒤 반드시 재시도) | 설비 담당: 제어기 전원·통신, 커튼 걸림 | 현장 조치 후 "재시도" → 문이 열림을 보고하면 정상 | 설비별 고장 이력 |
| 화재 경보 | 화재 수신기 신호(`facility/v1/fire/state`) | FIRE 모드: 신규 해제·배정 중단, 차량은 이미 받은 구간 끝(문턱·교차로가 아닌 곳)에서 정지, 고속문 닫힘. 일시정지·재개 명령 거부 | 지도에서 피난로·방화문 앞에 선 차량 확인, 막고 있으면 원격 조종으로 비켜 세움 | 대피, 방화문 확인 | 경보 해제 → 전체 일시정지로 전환 → 현장 확인 뒤 운영자가 재개 | 감사 로그, 정지 위치 |
| 교착 | 대기 관계 순환 2초 유지 | 한 대 재계획 또는 비켜서기 | 30초 안에 안 풀리면: 우선순위 낮은 작업 취소 또는 원격 조종 | 필요하면 한 대 수동 이동 | 자원 해제 확인 | 교착 위치 반복 여부(혼잡 레이어) |
| 장시간 정지 | 대기 사슬의 뿌리가 120초 정지(사람·수동 지게차 대기와 협업 구역의 사람 대기는 300초) | 우회 재탐색 반복 | 원인 확인 후 제거 또는 작업 취소·재할당 | 원인 제거 | 경로 해제 | 같은 지점 반복 시 동선 검토 |
| 배터리 위험 | 10% 미만이고 충전 중 아님 | 30% 미만부터 신규 배정 없이 충전 대기(충전 중이면 60%까지 충전), 7% 미만은 충전기 선점(60% 넘게 찬 대기 차량을 비킴) | 현 작업 유지 가능 여부 판단, 불가하면 재할당 후 충전 | 방전 시 수동 이동 | 충전 | — |
| 원격 조종 인계 | 운영자 명령(확인 필요) | 작업 분리, 0.6초 데드맨, 시뮬레이션 1배속 | 로컬 뷰로 주변을 확인하며 조작 | — | 자동 복귀 명령 | 조종 중 예약 침범은 점유-예약 불일치로 기록 |
| 구역 대피 | 운영자 명령(확인 필요) | 구역 봉쇄 + 구역 안 로봇을 밖으로 이동 | 대피 완료 확인 | 대피 경로 확인 | 봉쇄 해제 | 감사 로그 |
| 관제 내부 오류 | 관제 주기 예외 | FMS_INTERNAL_ERROR, 전체 일시정지(차량은 base 끝에서 정지), 주기는 계속 | 이벤트 기록·서비스 로그 확인, 현장 안전 확인 뒤 재개. 반복되면 관제 서비스 재기동(5절) | — | 운영자 재개 | 오류 내용, 개발 보고 |

## 4. 비상 계획표

MiR Fleet 문서의 비상 계획표 형식(상황 / 위험 / 예방 조치 / 현장 조치)입니다(R2 B-3).

| 상황 | 위험 | 예방 조치 | 현장 조치 |
|---|---|---|---|
| 관제 서버 정지 | 신규 작업·예약 갱신 중단. 차량은 받은 구간 끝에서 정지 | UPS, 차량 측 released 구간 밖으로는 나가지 않는 VDA 5050 설계, 작업·예약 스냅숏의 SQLite 저장 | 5절 재기동 절차 |
| 무선망 장애 | 다수 차량 통신 두절, 작업 정체 | AP 이중화, 채널 사용률 감시(60% 초과 시 지연 증가, R2 B-1), 짧은 끊김은 알림으로만 표시 | 두절 차량 위치 확인, 필요하면 해당 구역 봉쇄. 복구 후 동기화 확인 |
| 브로커 장애 | 관제와 차량 사이 메시지 전체 중단 | 브로커 이중화 또는 빠른 재기동, 관제·차량 모두 자동 재접속 | 브로커 복구 → 차량 ONLINE(retained connection) 확인 → 재동기화 확인 |
| 차량 방전 | 통로 한가운데 정지, 뒤 차량 정체 | 30% 미만 신규 배정 중단·충전, 10% 미만 알람, 7% 미만 충전기 선점 | 수동 모드로 가까운 충전기까지 이동하거나 밀어서 회수 |
| 인프라 카메라 두절 | 사각지대 사람을 관제가 모름 | 사람 구역 전체 자동 감속, 감지 피드 감시. 사람 보호는 차량 탑재 인원 감지가 담당 | 복구 전까지 사각지대 봉쇄 검토 |
| 고속문 고장 | 방화벽을 건너는 작업 지연 | 문 고장 판정·우회 자동화. 남·북 두 문과 동측 복귀로(x = 76.8 m)로 어느 문 하나가 고장 나도 출고 스테이징에 갈 수 있음 | 설비 담당 호출, 남은 문으로 우회 확인 |
| 화재 경보 | 대피로·방화문 앞 차량 정지 | 화재 수신기 → 관제 FIRE 모드(신규 해제 중단, 문턱·교차로 정차 금지 유지), 방화 셔터는 화재 수신기에 배선 연동 | 대피 → 막은 차량 원격 조종으로 이동 → 경보 해제 후 현장 확인 → 구역별 순차 재개 |
| 레이아웃·설정 손상 | 잘못된 경로·속도 | 기동 시 레이아웃 검증(차종별 강연결, 도달 불가 노드), LIF 파일 변경 관리 | 이전 버전 LIF로 되돌리고 재기동 |

## 5. 관제 서비스 재기동

실운영 서비스(`fleet.fms`)의 재기동 절차입니다. 재동기화는 자동이며, 관제원은 결과를 확인합니다([INTEGRATION.md](INTEGRATION.md) 8절).

1. 재기동 전: 현재 모드와 진행 중 작업 수를 인수인계 메모로 남깁니다(가능하면 전체 일시정지 후).
2. 서비스를 다시 띄웁니다. 운영 모드가 "재동기화(RESYNC)"로 표시되고, 직전 스냅숏의 예약이 먼저 되살아납니다. 이 동안 재개 명령은 거부됩니다.
3. 차량이 state를 보내면 하나씩 대조됩니다. 이벤트 기록에서 다음을 확인합니다.
   - "재동기화: 주문 … 이어서 진행": 차량이 이전 order를 계속 달리고 있어 이어받음
   - "재동기화: 보내지 못한 주문 … 전송": 재기동 직전에 보내지 못한 order를 다시 보냄
   - "재기동 사이 주문 종료" 또는 "알 수 없는 주문 진행 중: 취소 후 재배정": 스냅숏과 차량이 다름. 적재 전 작업은 대기열로 돌아가고, 적재 후 작업은 "적재물 현장 확인"으로 실패 처리됩니다. 현장 인원이 적재물 상태를 확인하고 WMS와 맞춥니다
4. 15초가 지나면 "재동기화 완료"가 뜨고 정상 운영으로 돌아갑니다. 그때까지 state가 오지 않은 차량은 예약을 유지한 채 "무응답"으로 표시되며, 3절의 통신 두절 절차를 따릅니다.
5. 정상 운영으로 돌아오면 점유-예약 불일치 알람이 없는지, 감사 로그 검증(`/api/audit/verify`)에 문제가 없는지 확인합니다.

  -30 s  …

  +10 s  …
